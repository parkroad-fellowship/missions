# Mobile App Architecture

## Overview

PRF Missions follows a modular Flutter architecture centered around feature isolation, Cubit state management, and clear domain boundaries.

**Stack summary:** Flutter ^3.47 / Dart ^3.12 · `bloc`/`flutter_bloc` (Cubits + freezed states) · `get_it` (DI) · `auto_route` (navigation) · `dio` (networking) · Hive CE (persistence) · Firebase (auth, messaging, analytics, crashlytics, remote config) · PostHog (analytics) · Shorebird (code push).

### Features (`lib/features/`)

Five top-level features. Every routable screen follows the same convention:

- `<name>.dart` — a `@RoutePage()` widget that delegates to adaptive siblings.
- `_handset.dart`, `_tablet.dart`, `_shared.dart` — layout implementations selected via adaptive helpers from the shared design package (`prf_design`). Tablet (>= 600dp) restructures layouts; see `DESIGN.md`.
- `actions/<action_name>/` — leaf forms/sheets for a single action.
- `cubit/` — one Cubit per screen or section; freezed states.
- `di/<feature>_module.dart` — service + BlocProvider registration.

| Feature | Contents |
|---|---|
| `auth` | Sign-in (email, Google), social login cubits |
| `events` | Events list/details, subscriptions, event media |
| `home` | Largest surface: account, announcements, FAQs, giving, landing, prayer requests, student enquiries, wrapped; 7 own DI modules |
| `lms` | Course/module/lesson details |
| `missions` | Missions list, mission details with nested sections (expenses, gallery, sessions, souls, subscribers, debrief notes, requisitions, questions) |

Leaf widgets may live deeply nested (e.g. `features/missions/mission_details/widgets/expenses/cubit/`), but their wiring stays centralized in the feature's `di/` module.

## Startup Sequence

Each flavor entry point calls `bootstrap()` in `lib/bootstrap.dart`:

1. Register `BlocObserver`, Manrope font license, timezone data.
2. Initialize Firebase.
3. `DIContainer.setup()` then `initializeDatabases()` (Hive).
4. Release builds only: read Shorebird patch number and install Crashlytics error handlers (`FlutterError.onError`, `PlatformDispatcher.instance.onError`).
5. Sync request signing keys with the backend (`RequestSigner.syncWithServer`).
6. Init Remote Config, analytics, sockets (if a user profile exists in Hive), identify user, upload FCM token via `AuthService.updateProfile`.
7. Run the app starting at `DecisionPage`, which routes to sign-in or landing based on auth state.

## Dependency Injection

Manual `get_it` registration — no codegen. `lib/di/di_container.dart` exposes the global `getIt` plus `DIContainer`:

- **Core first:** `CoreModule` (HTTP, Hive, base services), then `FirebaseModule` and `MediaModule`.
- **Domain modules:** Account, Announcements, Auth, Enquiries, Events, Expenses, HomeShared, Lms, Members, Missions, Payments, Prayer — each under its feature's `di/` directory.
- **Cubits:** every module also exposes `registerCubits(getIt)`; `DIContainer.registerCubits()` aggregates them into the root `MultiBlocProvider` (theme first, since MaterialApp depends on it).

To add a Cubit or service: register it in the owning feature's module — not ad hoc at the usage site.

## State Management

Plain `bloc` v9 Cubits with freezed states. Two shared base classes in `lib/utils/crud/` cover most data screens:

- `ResourceCubit<T>` — list read/write model over an API service + Hive DB service (refresh/pagination semantics).
- `SingleResourceCubit<T>` — item read model. Hive is the source of truth: after writes the entity is persisted, and UI updates arrive by watching the Hive item stream (`watchItem`), never from raw API responses.

Conventions:

- Naming: `<domain>_resource_cubit.dart` for list/detail resources; plain `<action>_cubit.dart` for command-style flows (e.g. `subscribe_cubit.dart`).
- States come from `ResourceState` (`initial/itemLoading/itemLoaded/itemError`) unless a flow needs custom fields (then freezed per-cubit states).
- List state and item state are owned by separate cubits — a detail Cubit never mutates list state.

## Routing

`auto_route` with codegen (`router.gr.dart`). Config lives in `PRFSuperAppRouter` (`lib/utils/router/router.dart`) with path constants per route; `guards/auth_guard.dart` protects authenticated routes. Screens annotate pages with `@RoutePage()` and navigate through typed router extensions. Deep links (notification taps) use `router.replaceAll([...])`.

## Data Layer

**Network** (`lib/utils/http/`): `NetworkUtil` wraps dio; `request_signer.dart` signs requests against server-synced keys; `retry_interceptor.dart` handles transient failures; Azure Blob upload helper for media. Web uses conditional imports (`utils/http/multiplatform/`).

**API services** (`lib/services/api/`): abstract `BaseAPIService<T>` plus ~30 domain services. Services are transport only — no caching or business logic.

**Models** (`lib/models/remote/`): freezed + json_serializable DTOs per domain folder, mapping to/from Hive locals.

**Persistence** (`lib/services/local_storage/hive/`): `HiveService` facade over all boxes, split into:

- `kv/` — key-value stores (`AuthHiveService`, `SettingsHiveService`) on a shared base.
- `db/` — typed entity CRUD services (~30) on `BaseHiveDbService<T>`, exposing watch streams consumed by resource cubits.

Adapters are generated in `lib/hive/hive_adapters.g.dart` via `@GenerateAdapters`.

## Cross-Cutting Services

- **Analytics** (`lib/services/analytics/`): abstract `AnalyticsService` implemented by `UnifiedAnalyticsService`, which dual-writes PostHog (EU host, session replay) and Firebase Analytics. Collection is gated to release production builds only.
- **Error reporting** (`lib/services/errors/`): `UnifiedErrorReportingService` → Crashlytics, installed globally in bootstrap for release builds.
- **Push notifications**: FCM messages filtered on `data['target_app'] == 'missions_app'` (`firebase_messaging_service.dart`) and surfaced as local notifications via awesome_notifications (`notification_service.dart`); tap handling switches on `PRFNotificationType` payload to deep-link into missions/events/prayer/giving. Recurring local prompts (prayer, Friday giving) are scheduled with timezone-aware calendars; permission UX is gated through `SettingsHiveService`.
- **Realtime**: Pusher Channels (`socket_service.dart`), initialized at bootstrap when a profile exists.
- **Media**: recording, playback, download, and a failed-upload retry queue (`services/media/`, `models/local/`).
- **Code push**: Shorebird releases per flavor (`shorebird.yaml`); current patch number reported as a Crashlytics custom key.

## Codegen Workflow

Generated files (`*.g.dart`, `*.freezed.dart`, `router.gr.dart`) must be regenerated after touching annotated models/routes:

```sh
make gen      # dart run build_runner build (freezed, json, auto_route, hive)
make l10n     # flutter gen-l10n (arb/app_en.arb -> app_localizations)
```

CI verifies codegen is committed and reproducible by running `build_runner` and failing on diffs. `versioning/build_version.dart` is generated by the `build_version` builder.

## Feature Isolation Guardrails

`scripts/architecture_guardrails.sh` (run via `make arch-check`) enforces:

- No `_index.dart` barrel imports (baseline 0).
- Non-feature → feature imports must not grow past baseline (54); route new usage through feature public APIs.
- **Hard fail** on any top-level feature-to-feature import (e.g. `auth` importing `home` internals).

`make arch-edges` (`scripts/feature_import_edges.sh`) reports current edge counts when refactoring.

## Testing

Current state, documented honestly:

- **Unit/widget tests:** none yet — `test/` contains only `.gitkeep`. `mocktail` is declared but unused; `bloc_test` is commented out in `pubspec.yaml`. There is no `flutter test` step in CI or the Makefile.
- **Integration tests:** Patrol-based, in `integration_test/`. `screenshot_test.dart` holds a full page-by-page walkthrough that is currently commented out (it predates the infinite animations from `flutter_animate`; helpers remain in `integration_test/utils/`: `screenshot_helper.dart`, `test_config.dart`). Patrol targets/flavors are configured in the `patrol:` block of `pubspec.yaml` and runnable via `make screenshots` / `make patrol-dev` (development flavor).

## CI/CD

GitHub Actions workflows (`.github/workflows/`):

- **pr-check.yaml** (PRs to main): JDK 21 + Flutter setup → `dart format --set-exit-if-changed lib test` → `build_runner build` (codegen drift check) → `flutter analyze lib`. Architecture guardrails exist but are not yet enforced here.
- **deploy-development.yaml / deploy-staging.yaml** (manual dispatch): flavored APK builds → Firebase App Distribution.
- **deploy-production.yaml**: secret-injected AAB build → Play Store (Fastlane `supply`), Huawei AppGallery, Firebase App Distribution, Crashlytics debug symbol upload.

Composite actions: `.github/actions/flutter-setup`, `android-setup` (keystore signing), `free-disk-space`.

## Release Readiness

Run before cutting a release:

```sh
make fmt          # dart fix --apply && dart format lib test
make gen          # ensure generated code is up to date
make l10n         # regenerate localizations if arb changed
make arch-check   # feature isolation guardrails pass
flutter analyze lib
```

Builds:

```sh
make apk          # production APK
make ipa          # production IPA
make aab-shore    # Shorebird Android release (obfuscated, symbols split)
make ios-shore    # Shorebird iOS release
make web          # production web build (Firebase Hosting via deploy-* targets)
```

> Note: `make aab` currently targets `lib/main_debug.dart` instead of `lib/main_production.dart` — verify before using it for store uploads; prefer `aab-shore`/CI.
